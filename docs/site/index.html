TensorGuard v0.1

A static verifier for PyTorch models. It reads your nn.Module, builds a computation graph, and uses Z3 to prove the absence of shape errors, device mismatches, phase bugs, and dead code—or finds a concrete counterexample. No runtime, no test inputs needed.

source pypi paper

What it checks

TensorGuard statically verifies five properties simultaneously, using a product of abstract domains backed by a single Z3 query.

DomainTracksCatches
ShapeTensor dimensions and sizes through every opLinear/Conv channel mismatches, bad reshapes, cat dimension errors, broadcast failures

Phaseself.training flag across branchesLayers sized correctly in train but wrong in eval (or vice versa)

All five analyses run in a single pass over a computation DAG extracted from the AST. The shape analysis uses CEGAR (counterexample-guided abstraction refinement) to stay both precise and decidable.

Given forward(self, x) with declared input shape (batch, 3, 224, 224), TensorGuard propagates symbolic shapes through every layer, branching on self.training to cover both train and eval paths. If it finds any assignment to the symbolic variables that causes a crash, it reports UNSAFE with a concrete witness. Otherwise, the model is proved safe for all inputs of that shape.

Formal foundations

Refinement types for tensors

We type tensors as refinement types over a base type $\texttt{Tensor}$:

$$\tau ::= \{ t : \texttt{Tensor} \mid \phi(\text{shape}(t), \text{dev}(t), \text{grad}(t), \text{phase}) \}$$

where $\phi$ is a formula in the combined theory $\mathcal{T}_{\text{shape}} \times \mathcal{T}_{\text{dev}} \times \mathcal{T}_{\text{grad}} \times \mathcal{T}_{\text{phase}} \times \mathcal{T}_{\text{live}}$.

The shape domain

Shapes live in $\mathbb{N}^*$—sequences of positive integers. Each layer imposes constraints. For a linear layer $\texttt{Linear}(d_{\text{in}}, d_{\text{out}})$:

$$\frac{\Gamma \vdash e : \text{Tensor}[s_1, \ldots, s_{n-1}, d_{\text{in}}]} {\Gamma \vdash \texttt{Linear}(d_{\text{in}}, d_{\text{out}})(e) : \text{Tensor}[s_1, \ldots, s_{n-1}, d_{\text{out}}]}$$

For $\texttt{Conv2d}(c_{\text{in}}, c_{\text{out}}, k, s, p)$ on input $[B, c_{\text{in}}, H, W]$:

$$H_{\text{out}} = \left\lfloor \frac{H + 2p - k}{s} \right\rfloor + 1 \qquad W_{\text{out}} = \left\lfloor \frac{W + 2p - k}{s} \right\rfloor + 1$$

Device and phase theories

Devices form a finite domain $\mathcal{D} = \{\texttt{cpu}, \texttt{cuda:0}, \ldots\}$ with the constraint that binary ops require both operands on the same device. Buffers registered with register_buffer start on CPU and must be explicitly moved. TensorGuard checks: if the input arrives on cuda:0, does every buffer end up there too?

$$\frac{\Gamma \vdash e_1 : \tau[\text{dev}=d_1] \quad \Gamma \vdash e_2 : \tau[\text{dev}=d_2]} {\Gamma \vdash e_1 + e_2 : \tau[\text{dev}=d_1]} \quad \text{only if } d_1 = d_2$$

Phase tracking splits the analysis at if self.training: branches. Each branch gets a separate constraint set, so a model can be SAFE in training but UNSAFE in eval (or vice versa). The product domain joins them:

$$\text{result} = \text{SAT}(\phi_{\text{shape}} \wedge \phi_{\text{dev}} \wedge (\phi_{\text{train}} \vee \phi_{\text{eval}}) \wedge \phi_{\text{grad}} \wedge \phi_{\text{live}})$$

CEGAR loop

When symbolic shapes lead to undecidable nonlinear arithmetic, TensorGuard uses CEGAR: start with an abstract check, and if it reports a potential bug, concretize the symbolic dimensions and re-check. This terminates because dimension variables range over finite positive integers in practice.

The refinement loop:

$$\text{AbstractCheck}(\phi) \xrightarrow{\text{UNSAFE}} \text{Concretize}(\phi, \vec{v}) \xrightarrow{\text{check}} \begin{cases} \text{UNSAFE} & \text{real bug} \\ \text{SAFE} & \text{refine } \phi \end{cases}$$

Soundness

Theorem. If TensorGuard reports SAFE, then for all inputs matching the declared shape signature, the model's forward method will not raise a shape, device, or broadcasting error at runtime.

(Proof by induction on the computation DAG; each transfer function is sound w.r.t. PyTorch semantics. See paper, §4.)

Decidability

Theorem. The combined theory $\mathcal{T}_{\text{shape}} \times \mathcal{T}_{\text{dev}} \times \mathcal{T}_{\text{phase}} \times \mathcal{T}_{\text{grad}} \times \mathcal{T}_{\text{live}}$ is decidable for the fragment of constraints generated by PyTorch's standard layer API. This follows from each individual theory being decidable and the Nelson-Oppen combination conditions being satisfied (disjoint signatures, stably infinite theories).

Verified examples

Every example below was run through TensorGuard. The output shown is the actual verifier output. These are not synthetic “Linear expects 10, got 20” mismatches—they are realistic architectural bugs drawn from real model patterns.

device shape Positional encoding buffer stays on CPU

A common transformer pattern: pre-computed positional encodings stored as a buffer. When the model is moved to GPU, register_buffer tensors are moved too—but only if .to(device) is called on the module. TensorGuard checks what happens when input arrives on CUDA and the buffer was never moved.

model.py 
class PositionalEncoder(nn.Module):
    def __init__(self, d_model=512, max_len=200):
        super().__init__()
        self.proj = nn.Linear(d_model, d_model)
        self.register_buffer('pe', torch.randn(1, max_len, d_model))

    def forward(self, x):
        # x: [batch, seq_len, 512]
        return self.proj(x) + self.pe[:, :x.size(1), :]
$ tensorguard verify model.py -s x=batch,128,512 [DEVICE-MISMATCH] Device mismatch: proj output is on cuda:0 but self.pe is on cpu (buffer registered on CPU may mismatch CUDA input) Result: UNSAFE (191ms)

The shape analysis also catches a subtler issue: the slice self.pe[:, :x.size(1), :] produces shape (1, 128, 512), which needs to broadcast against the projected output (batch, 128, 512). That works—but the device mismatch means it would crash before broadcasting even gets a chance.

phase shape Train/eval heads with mismatched dimensions

Some architectures use different classification heads for training (large vocabulary, aux losses) and inference (final classes). If the backbone output doesn't match both heads, one phase crashes.

dual_head.py 
class DualHeadClassifier(nn.Module):
    def __init__(self):
        super().__init__()
        self.backbone = nn.Linear(512, 256)
        self.train_cls = nn.Linear(256, 100)  # fine in training
        self.eval_cls = nn.Linear(128, 10)    # expects 128, gets 256

    def forward(self, x):
        h = self.backbone(x)
        if self.training:
            return self.train_cls(h)
        else:
            return self.eval_cls(h)  # BUG: 256 ≠ 128
$ tensorguard verify dual_head.py -s x=batch,512 [SHAPE-INCOMPATIBLE] Linear expects last dim=128, got 256 (in eval branch) Result: UNSAFE (17ms)

This passes all training tests. Only at deployment, when model.eval() is called, does it crash. TensorGuard checks both phases automatically.

cat Multi-scale feature fusion with spatial mismatch

Feature pyramid networks concatenate features from different resolutions. If a stride-2 convolution halves the spatial dims but the cat is along channels (dim=1), the spatial dims must still match.

fpn.py 
class FeatureFusion(nn.Module):
    def __init__(self):
        super().__init__()
        self.branch_a = nn.Conv2d(3, 64, 3, padding=1)
        self.branch_b = nn.Conv2d(3, 64, 3, stride=2, padding=1)
        self.merge = nn.Conv2d(128, 64, 1)

    def forward(self, x):
        a = self.branch_a(x)   # [B, 64, 32, 32]
        b = self.branch_b(x)   # [B, 64, 16, 16]  ← stride=2
        f = torch.cat([a, b], dim=1)  # BUG
        return self.merge(f)
$ tensorguard verify fpn.py -s x=batch,3,32,32 [SHAPE-INCOMPATIBLE] cat: dimension 2 mismatch: 32 vs 16 (cat along dim=1) Result: UNSAFE (77ms)

The fix is to upsample b back to 32×32 before concatenating, or to use an FPN-style lateral connection with interpolation. TensorGuard traces the spatial dimension through the strided convolution and catches the mismatch at the cat call.

broadcast device Channel-wise scale with wrong buffer shape

A learnable scale vector should have shape (C,) or (1, C, 1, 1) to broadcast against (B, C, H, W). If the number of channels doesn't match, broadcasting fails with a cryptic error at runtime.

scale.py 
class ScaledConv(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 64, 3, padding=1)
        self.register_buffer('scale', torch.randn(32))  # BUG: 32 ≠ 64

    def forward(self, x):
        out = self.conv(x)          # [B, 64, H, W]
        return out * self.scale     # can't broadcast (64,) and (32,)
$ tensorguard verify scale.py -s x=batch,3,16,16 [SHAPE-INCOMPATIBLE] Cannot broadcast (B, 64, 16, 16) and (32) [DEVICE-MISMATCH] out is on cuda:0 but self.scale is on cpu Result: UNSAFE (59ms)

Two bugs in four lines. The shape mismatch would crash even on CPU; the device mismatch would crash on GPU even if shapes matched. TensorGuard reports both.

dead device Computed result never returned

In detection models, eval-time post-processing sometimes computes a result but forgets to return it, falling through to the training-time return instead.

detector.py 
class Detector(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 64, 3, padding=1)
        self.head = nn.Conv2d(64, 10, 1)
        self.register_buffer('bias_grid', torch.randn(1, 1, 8, 8, 2))

    def forward(self, x):
        feat = self.head(self.conv(x))
        if not self.training:
            B, C, H, W = feat.shape
            processed = feat.view(B, 1, C, H, W)
            result = processed + self.bias_grid  # computed...
        return feat  # ...but never used
$ tensorguard verify detector.py -s x=batch,3,16,16 [DEAD-OUTPUT] Result 'result' is computed but never used or returned [DEVICE-MISMATCH] processed is on cuda:0 but self.bias_grid is on cpu [SHAPE-INCOMPATIBLE] Cannot broadcast (B,1,10,16,16) and (1,1,8,8,2) Result: UNSAFE (139ms)

Three bugs. The liveness analysis catches the dead output (the result variable is assigned but never flows to a return). The device analysis catches the CPU buffer. And the shape analysis catches the broadcast mismatch between (B,1,10,16,16) and (1,1,8,8,2). Any one of these would cause incorrect behavior or a crash.

shape Channel mismatch through a deep conv stack

In deep networks, a refactoring changes the channel count in one stage but not in a downstream lateral connection. The bug is three layers away from the declaration.

backbone.py 
class Backbone(nn.Module):
    def __init__(self):
        super().__init__()
        self.stage1 = nn.Sequential(
            nn.Conv2d(3, 64, 3, padding=1),
            nn.BatchNorm2d(64), nn.ReLU())
        self.stage2 = nn.Sequential(
            nn.Conv2d(64, 128, 3, padding=1),
            nn.BatchNorm2d(128), nn.ReLU())
        self.stage3 = nn.Sequential(
            nn.Conv2d(128, 256, 3, padding=1),
            nn.BatchNorm2d(256), nn.ReLU())
        # lateral was written for stage2 output (128ch)
        # but now receives stage3 output (256ch)
        self.lateral = nn.Conv2d(128, 64, 1)

    def forward(self, x):
        x = self.stage1(x)
        x = self.stage2(x)
        x = self.stage3(x)
        return self.lateral(x)  # BUG: 256 ≠ 128
$ tensorguard verify backbone.py -s x=batch,3,32,32 [SHAPE-INCOMPATIBLE] Conv2d expects 128 input channels, got 256 Result: UNSAFE (63ms)

TensorGuard propagates the channel dimension through all three stages and catches the mismatch at the lateral connection. This is the kind of bug that survives code review because the Conv2d(128, 64, 1) looks right—you have to trace the data flow to see that stage3 changed the channel count to 256.

shape Flatten size miscalculation after pooling

A classic CNN-to-MLP transition bug: the linear layer's input features are computed by hand and don't match the actual flattened size after pooling.

cnn.py 
class CNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 64, 3, padding=1)
        self.pool = nn.AdaptiveAvgPool2d(4)
        # 64 * 4 * 4 = 1024, not 512
        self.fc = nn.Linear(512, 10)

    def forward(self, x):
        x = self.conv(x)
        x = self.pool(x)
        x = x.view(x.size(0), -1)  # [B, 1024]
        return self.fc(x)           # expects 512
$ tensorguard verify cnn.py -s x=batch,3,32,32 [SHAPE-INCOMPATIBLE] Linear expects last dim=512, got 1024 Result: UNSAFE (43ms)

TensorGuard symbolically evaluates the pool output shape, computes the product $64 \times 4 \times 4 = 1024$, and checks it against the linear layer's declared input features.

shape Residual connection after projection

A transformer block that projects to a different dimension before the residual add. The pre-norm and post-projection tensors have incompatible shapes.

transformer.py 
class TransformerBlock(nn.Module):
    def __init__(self, d=512):
        super().__init__()
        self.attn = nn.MultiheadAttention(d, 8)
        self.norm = nn.LayerNorm(d)
        self.proj = nn.Linear(d, 256)  # projects down

    def forward(self, x):
        attn_out, _ = self.attn(x, x, x)
        x = self.norm(x + attn_out)
        return x + self.proj(x)  # BUG: (seq,B,512) + (seq,B,256)
$ tensorguard verify transformer.py -s x=seq,batch,512 [SHAPE-INCOMPATIBLE] Cannot broadcast (seq, B, 512) and (seq, B, 256) Result: UNSAFE (68ms)

phase device shape Phase-gated detection head with three bugs

An object detection head that applies anchor offsets only during inference. The training path is clean; the eval path has a shape, device, and broadcast bug.

detection_head.py 
class DetectionHead(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 64, 3, padding=1)
        self.head = nn.Conv2d(64, 20, 1)
        self.register_buffer('anchors', torch.randn(1, 1, 8, 8, 4))

    def forward(self, x):
        feat = self.head(self.conv(x))
        if not self.training:
            B, C, H, W = feat.shape
            out = feat.view(B, 1, C, H, W)
            out = out + self.anchors  # three bugs here
        return feat
$ tensorguard verify detection_head.py -s x=batch,3,16,16 [SHAPE-INCOMPATIBLE] Cannot broadcast (B,1,20,16,16) and (1,1,8,8,4) [DEVICE-MISMATCH] feat is on cuda:0 but self.anchors is on cpu [DEVICE-MISMATCH] out is on cuda:0 but self.anchors is on cpu Result: UNSAFE (78ms)

This is a cross-theory bug: the shape theory catches the broadcast failure, the device theory catches the CPU/CUDA mismatch, and the phase theory confirms these bugs only manifest in eval mode. All three theories contribute to the diagnosis in a single 78ms analysis.

safe Correct DenseNet block

Not every model has bugs. TensorGuard also proves models correct.

densenet.py 
class DenseBlock(nn.Module):
    def __init__(self, in_ch=64, growth=32, layers=4):
        super().__init__()
        self.convs = nn.ModuleList()
        for i in range(layers):
            self.convs.append(nn.Sequential(
                nn.BatchNorm2d(in_ch + i * growth),
                nn.ReLU(),
                nn.Conv2d(in_ch + i * growth, growth, 3, padding=1)))

    def forward(self, x):
        features = [x]
        for conv in self.convs:
            out = conv(torch.cat(features, dim=1))
            features.append(out)
        return torch.cat(features, dim=1)
$ tensorguard verify densenet.py -s x=batch,64,32,32 Result: SAFE (68ms) No bugs found. Model is verified for all inputs of shape (batch, 64, 32, 32).

Usage

Point it at any file containing an nn.Module:

# Verify with declared input shapes
tensorguard verify model.py -s x=batch,3,224,224

# Check both train and eval phases
tensorguard verify model.py -s x=batch,3,224,224 --check-phases

# Include device analysis (CPU/CUDA mismatch detection)
tensorguard verify model.py -s x=batch,3,224,224 --check-devices

# JSON output for CI integration
tensorguard verify model.py -s x=batch,3,224,224 --format json

Python API

from tensorguard import verify_module

result = verify_module("model.py",
    input_shapes={"x": ("batch", 3, 224, 224)},
    check_devices=True,
    check_phases=True)

print(result.status)      # "SAFE" or "UNSAFE"
print(result.duration_ms) # analysis time
for bug in result.bugs:
    print(bug.message)
