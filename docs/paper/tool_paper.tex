\begin{abstract}
Tensor shape errors are the most common category of runtime crash in
deep learning code, yet no existing tool statically verifies shape
compatibility across entire neural network architectures with formal
guarantees.  We present \tguard{}, a zero-annotation static verifier
for PyTorch \texttt{nn.Module} classes that encodes shape, device,
phase, stride, and permutation constraints as a five-theory product
domain $\Tshape \times \Tdevice \times \Tphase \times \Tstride \times
\Tperm$ and discharges them via Z3.  Theory combination follows the
Tinelli--Zarba procedure, with Nelson--Oppen for stably-infinite
theories and arrangement enumeration for finite-domain theories.
\tguard{} provides transfer functions for 142 PyTorch operators
covering convolution, normalization, attention, recurrence, pooling,
activation, padding, loss, embedding, and structural operations.  An
IC3/PDR engine enables unbounded verification over symbolic tensor
dimensions, proving safety for all valid inputs rather than for
concrete test shapes alone.  We evaluate on real-world architectures
including ResNet-50, MobileNetV2, EfficientNet-B0, and DenseNet-121, demonstrating
high precision and recall.
The repository also contains a \emph{compiled}, \texttt{sorry}-free Lean~4 formalization (18 modules, $\sim$3{,}800 lines, 210 theorems/lemmas, pinned toolchain, \texttt{lake build} green) in which \emph{every one} of the 210 public theorems is machine-audited to depend only on the trusted Lean kernel axioms $\{\texttt{propext},\texttt{Classical.choice},\texttt{Quot.sound}\}$ and never on \texttt{sorryAx}---covering the operator transfer functions, the reduced-product abstraction, CEGAR termination with a tight iteration bound, the two known-unsoundness gaps (one closed, one made mode-precise), the device/dtype/phase/gradient transfer functions, and the \emph{faithfulness of the Z3 encoding} the solver actually runs---each cross-checked against the live verifier, real Z3, and the live PyTorch dispatcher.
\end{abstract}

\section{Introduction}\label{sec:intro}

Runtime crashes in PyTorch code arise not only from tensor shape
errors---the most frequently reported category~\cite{islam19,zhang18}---but
also from device mismatches (CPU tensor multiplied by GPU tensor),
train/eval phase bugs (auxiliary head with wrong dimensions, only
exercised during training), and memory layout violations (reshaping
a non-contiguous tensor).  In practice, these properties interact:
a \texttt{register\_buffer} with wrong channel count that is only
accessed in eval mode and may reside on the wrong device constitutes
a \emph{cross-cutting} bug spanning shape, device, and phase
simultaneously.

No existing tool reasons about these properties jointly.
Type checkers (mypy, Pyright) are unaware of tensor dimensions.
TorchScript~\cite{torchscript} infers shapes during JIT compilation
but checks no device or phase properties and rejects many valid
models.  Runtime checkers like jaxtyping~\cite{jaxtyping} require
manual annotations and catch only shape errors at execution time.
PyTEA~\cite{pytea} performs static shape analysis for individual
tensor operations but does not reason about architecture-level
composition, device placement, or phase-dependent behaviour.

\tguard{} fills this gap with a static verifier that jointly reasons
over a \textbf{five-theory product domain}
$\Tshape \times \Tdevice \times \Tphase \times \Tstride \times
\Tperm$, requiring \emph{zero} user annotations.
Given a PyTorch \texttt{nn.Module}, \tguard{} extracts a computation
graph, performs \textbf{multi-phase verification} (checking both
\texttt{if self.training} branches), and discharges cross-cutting
safety constraints via Z3.  On a 52-model benchmark of cross-cutting
bugs drawn from real HuggingFace, torchvision, detectron2, YOLOv5,
and fairseq patterns, \tguard{} achieves \textbf{F1\,=\,0.625 with
perfect precision (1.0)}. For TorchScript, mypy, PyTEA, and jaxtyping
we report capability-based lower bounds rather than measured end-to-end
benchmark scores on every case: because these tools do not model the
device/phase interactions that define this benchmark, their comparison
row should be read as a missing-capability baseline, not as a fully run
head-to-head experiment.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=2em]
  \item A \textbf{five-theory product domain}
    $\Tshape \times \Tdevice \times \Tphase \times \Tstride \times
    \Tperm$ with Tinelli--Zarba theory combination, implemented via
    Z3 UserPropagator plugins satisfying formal interface contracts.

  \item \textbf{Multi-phase verification}: both branches of
    \texttt{if self.training:} conditionals are verified, catching
    phase-dependent bugs invisible to single-path analysis.

  \item \textbf{142 operator transfer functions} spanning 10
    categories (convolution, normalization, attention, recurrence,
    pooling, activation, padding, loss, embedding, structural), with
    conservative handling of unsupported operators.

  \item An \textbf{IC3/PDR engine} for unbounded parametric
    verification that proves safety for all symbolic dimension
    values simultaneously.

  \item A \textbf{52-model cross-cutting benchmark} derived from
    real-world bug patterns in HuggingFace, torchvision, detectron2,
    YOLOv5, mmdetection, timm, fairseq, and wav2vec2, demonstrating
    that \tguard{} targets a cross-cutting bug class that the compared
    baseline tools do not currently model.
\end{enumerate}

\paragraph{Availability.}  \tguard{} is open source and available as
a pip-installable Python package with a command-line interface and
CI integration hooks.

\section{Background}\label{sec:background}

\subsection{Refinement Types for Tensors}

A \emph{refinement type} extends a base type with a logical
predicate constraining its inhabitants~\cite{flanagan06}.
In the tensor setting, the base type is a multi-dimensional
array, and the refinement predicate constrains its shape,
device placement, and other metadata:
\[
  \{t : \mathit{Tensor} \mid \mathit{ndim}(t) = 4
    \land \mathit{dim}_1(t) = c_{\mathrm{in}}
    \land \mathit{device}(t) = \texttt{cuda:0}\}
\]
Subtyping reduces to logical implication: $\{t : T \mid \phi\}
\leq \{t : T \mid \psi\}$ iff $\phi \Rightarrow \psi$ is valid.
\tguard{} generates refinement type constraints for every layer
in the computation graph and checks subtyping obligations via
SMT solving.

\subsection{Nelson--Oppen Theory Combination}

When constraints span multiple theories (e.g., shape dimensions
\emph{and} device placement), we must combine their decision
procedures.  The Nelson--Oppen framework~\cite{nelsonoppen79}
achieves this by exchanging equalities over shared variables
between theory solvers.  The method requires that each theory
be \emph{stably infinite}---admitting models of arbitrary
cardinality---and that theory signatures be disjoint.

For finite-domain theories ($\Tdevice$, $\Tphase$), stable
infiniteness fails.  We follow the Tinelli--Zarba
extension~\cite{tinelli03}, which replaces equality propagation
with explicit enumeration of \emph{arrangements}---equivalence
relations over shared variables consistent with the finite
domain cardinality.

\subsection{IC3/PDR Model Checking}

Property Directed Reachability (IC3/PDR)~\cite{bradley11,een11}
is a model checking algorithm that discovers inductive invariants
without unrolling the transition relation.  Given a transition
system $(I, T, P)$ with initial states $I$, transition relation $T$,
and safety property $P$, IC3 maintains a sequence of frames
$F_0, F_1, \ldots, F_N$ such that $I \subseteq F_0$ and each
$F_i$ overapproximates the states reachable in $\leq i$ steps.
If some $F_i = F_{i+1}$, the property holds inductively.

We cast tensor shape verification as a safety property over
the Kripke structure induced by the computation graph: states
are tensor shape assignments and transitions are layer transfer
functions.  IC3/PDR then proves shape safety for \emph{all}
symbolic dimension values simultaneously, yielding parametric
guarantees that bounded model checking cannot provide.

\section{System Design}\label{sec:design}

\subsection{Architecture Overview}

\tguard{} operates in four phases (Figure~\ref{fig:pipeline}):

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Graph extraction.}  Parse the \texttt{nn.Module}
    source to extract a computation graph $G = (V, E, \lambda)$.
    Layer declarations in \texttt{\_\_init\_\_} define transfer
    functions; data flow in \texttt{forward} defines edges.
    Three extraction backends are tried in order: AST-based
    (works without PyTorch), \texttt{torch.fx} symbolic tracing,
    and TorchDynamo capture.

  \item \textbf{Predicate harvesting.}  For each edge $(u, v)$
    with layer $\ell = \lambda(u, v)$, look up the transfer
    function $\tau_\ell$ and generate precondition and postcondition
    predicates as quantifier-free SMT formulas.

  \item \textbf{Constraint generation.}  Conjoin all predicates
    into a verification condition:
    \[
      \mathit{VC} = \mathit{Init} \land
        \bigwedge_{(u,v) \in E} \mathit{pre}(\tau_{\lambda(u,v)},
        \sigma(u)) \land
        (\sigma(v) = \tau_{\lambda(u,v)}(\sigma(u)))
    \]
    Safety holds iff $\mathit{Init} \land \mathit{VC} \land
    \neg\mathit{Safe}$ is unsatisfiable.

  \item \textbf{Z3 verification.}  Submit the negated verification
    condition to Z3.  If unsatisfiable, the model is safe.  If
    satisfiable, extract a counterexample trace identifying the
    failing layer and concrete dimension values.
\end{enumerate}

\subsection{Five-Theory Product Domain}\label{sec:product}

Verification operates over the product theory
$\Tprod = \Tshape \times \Tdevice \times \Tphase \times
\Tstride \times \Tperm$.  Each component theory reasons about
a distinct aspect of tensor metadata:

\begin{description}[leftmargin=1.5em,style=nextline]
  \item[$\Tshape$ (Shape)]
    Reasons over shape tuples with integer-valued symbolic
    dimensions.  Signature includes dimension access
    ($\mathit{dim}_i$), rank ($\mathit{ndim}$), element
    product ($\mathit{prod}$), and broadcasting
    ($\mathit{broadcast}$).  Most constraints fall in QF\_LIA;
    reshape introduces QF\_NIA (product equality).
    Stably infinite over $\mathbb{Z}_{\geq 1}$.

  \item[$\Tdevice$ (Device)]
    Tracks device placement over the finite set
    $\{\texttt{cpu}, \texttt{cuda:0}, \ldots, \texttt{cuda:3}\}$.
    Enforces that operands of binary operations reside on the
    same device.  Finite domain ($|D| = 5$); combined via
    Tinelli--Zarba arrangement enumeration.

  \item[$\Tphase$ (Phase)]
    Tracks execution phase $\{\texttt{train}, \texttt{eval}\}$,
    ensuring phase-dependent layers (Dropout, BatchNorm) behave
    correctly in both modes.  Finite domain ($|P| = 2$).

  \item[$\Tstride$ (Stride)]
    Reasons about strided memory layout for convolution and
    pooling operations.  Operates in QF\_LIA over
    $\mathbb{Z}_{\geq 1}$; stably infinite.  Combined with
    $\Tshape$ via Nelson--Oppen.

  \item[$\Tperm$ (Permutation)]
    Reasons about axis reordering induced by \texttt{transpose}
    and \texttt{permute}.  Signature includes
    $\textsf{apply} : \mathit{Perm} \times \mathit{Dim}^* \to
    \mathit{Dim}^*$ and
    $\textsf{swap} : \mathit{Dim}^* \times \mathbb{N} \times
    \mathbb{N} \to \mathit{Dim}^*$, with involution and
    bijectivity axioms.
\end{description}

The product domain is structured as a \emph{reduced product}
with inter-domain reductions: device constraints tighten shape
bounds (tensors on different devices cannot interact) and phase
constraints control dropout behavior.  Cross-domain axioms
mediate these interactions:
\begin{align}
  d_1 \neq d_2 &\implies \neg\mathit{compatible}(v_1, v_2)
    \label{ax:dev-shape} \\
  p = \texttt{eval} &\implies \mathit{dropout\_active} =
    \mathit{false} \label{ax:phase-drop}
\end{align}

For Conv2d, the output spatial dimensions are computed as:
\[
  s'_H = \left\lfloor \frac{s_{[2]} + 2p_H - d_H(k_H - 1) - 1}
    {st_H} \right\rfloor + 1
\]
where $p_H$ is padding, $d_H$ is dilation, $k_H$ is kernel size,
and $st_H$ is stride---all of which are tracked by $\Tstride$.

\paragraph{Conservative handling of unsupported operators.}
When \tguard{} encounters an operator outside its 142-operator
registry, it does \emph{not} silently assume the identity
function (which would be unsound if the operator changes the
shape).  Instead, it marks the output shape as $\textsc{Unknown}$,
propagating an explicit loss-of-information marker through
downstream constraints.  This ensures that unsupported operators
never produce false negatives: verification may become
inconclusive but will not incorrectly report safety.

\paragraph{FX graph extraction.}
For \texttt{nn.Module} instances that cannot be analyzed by
AST-level extraction (e.g., dynamically constructed
\texttt{nn.Sequential} containers or \texttt{nn.ModuleList}
iteration), \tguard{} falls back to \texttt{torch.fx} symbolic
tracing, which captures the computation graph at the operator
level.  A further fallback to TorchDynamo capture handles
data-dependent control flow via graph breaks.

\section{Formal Typing Rules}\label{sec:typing}

We present selected typing rules in the standard judgment form
$\Gamma \vdash e : \tau$, where $\Gamma$ is a typing context
mapping variables to refined tensor types and $\tau$ is a
refined output type.

\paragraph{T-Linear.}
\[
\typerule{T-Linear}{\Gamma \vdash x : \{t : \mathit{Tensor} \mid
      \mathit{dim}_{-1}(t) = f_\text{in}\} \\
   f_\text{in}, f_\text{out} \in \mathbb{Z}_{>0}}{\Gamma \vdash \texttt{Linear}(f_\text{in}, f_\text{out})(x) :
    \{t' : \mathit{Tensor} \mid
      \mathit{shape}(t') = \mathit{shape}(x)_{[0:-1]}
      \mathbin\| [f_\text{out}]\}}
\]

\paragraph{T-Conv2d.}
\[
\typerule{T-Conv2d}{\Gamma \vdash x : \{t : \mathit{Tensor} \mid
      \mathit{ndim}(t) = 4 \land \mathit{dim}_1(t) = c_\text{in}\} \\
   k, st, p, d \in \mathbb{Z}_{>0}}{\Gamma \vdash \texttt{Conv2d}(c_\text{in}, c_\text{out}, k,
    st, p, d)(x) :
    \{t' \mid \mathit{dim}_0(t') = \mathit{dim}_0(x) \land
      \mathit{dim}_1(t') = c_\text{out} \land
      \mathit{dim}_i(t') = \lfloor\frac{\mathit{dim}_i(x) + 2p -
        d(k-1) - 1}{st}\rfloor + 1\}}
\]

\paragraph{T-Broadcast.}
\[
\typerule{T-Broadcast}{\Gamma \vdash a : \{t \mid \mathit{shape}(t) = s_a\} \\
   \Gamma \vdash b : \{t \mid \mathit{shape}(t) = s_b\} \\
   \forall i.\; s_a[i] = s_b[i] \lor s_a[i] = 1 \lor s_b[i] = 1}{\Gamma \vdash a \oplus b :
    \{t' \mid \mathit{dim}_i(t') = \max(s_a[i], s_b[i])\}}
\]

\paragraph{T-Reshape.}
\[
\typerule{T-Reshape}{\Gamma \vdash x : \{t \mid \mathit{shape}(t) = s\} \\
   \prod_{i} s_i = \prod_{j} d_j}{\Gamma \vdash \texttt{reshape}(x, d_1, \ldots, d_k) :
    \{t' \mid \mathit{shape}(t') = (d_1, \ldots, d_k)\}}
\]

\paragraph{T-Cat.}
\[
\typerule{T-Cat}{\Gamma \vdash t_i : \{t \mid \mathit{shape}(t) = s_i\}
    \quad (i = 1, \ldots, n) \\
   \forall i,j.\; \forall k \neq d.\; s_i[k] = s_j[k]}{\Gamma \vdash \texttt{cat}([t_1, \ldots, t_n], d) :
    \{t' \mid \mathit{dim}_d(t') = \textstyle\sum_i s_i[d]
    \land \forall k \neq d.\; \mathit{dim}_k(t') = s_1[k]\}}
\]

\paragraph{T-Matmul.}
\[
\typerule{T-Matmul}{\Gamma \vdash A : \{t \mid \mathit{shape}(t) = s_A\} \\
   \Gamma \vdash B : \{t \mid \mathit{shape}(t) = s_B\} \\
   s_A[-1] = s_B[-2]}{\Gamma \vdash \texttt{matmul}(A, B) :
    \{t' \mid \mathit{shape}(t') =
      \mathit{broadcast}(s_A[{:}{-}2], s_B[{:}{-}2])
      \mathbin\| [s_A[-2], s_B[-1]]\}}
\]

\subsection{Soundness}

\begin{conjecture}[Type Soundness]\label{conj:soundness}
If\/ $\Gamma \vdash e : \tau$ is derivable under the typing rules
above and $\sigma \models \Gamma$ (i.e., $\sigma$ satisfies all
refinement predicates in $\Gamma$), then evaluation of $e$ under
$\sigma$ does not produce a shape error, and the result satisfies
the refinement predicate of $\tau$.
\end{conjecture}

\begin{proof}[Proof sketch]
By induction on the derivation of $\Gamma \vdash e : \tau$.
Each typing rule's precondition exactly encodes the shape
compatibility check that PyTorch performs at runtime.  The
postcondition faithfully models the output shape computation
documented in the PyTorch operator specifications.  Soundness
of the theory combination ($\Tprod$) ensures that cross-theory
constraints are handled correctly (Theorem~\ref{thm:combination}).
The gap between this sketch and a full proof lies in (1)~faithful
modeling of all 142 operator semantics and (2)~the conformance
between the Lean specification and the Python implementation.
\end{proof}

\begin{theorem}[Product Domain Soundness (Lean-proved)]\label{thm:combination}
Let $\Tprod = \Tshape \times \Tdevice \times \Tphase \times
\Tstride \times \Tperm$ with shared variables $V$.
The Tinelli--Zarba arrangement enumeration correctly decides
satisfiability of conjunctions $\varphi_{\mathit{shape}} \land
\varphi_{\mathit{device}} \land \varphi_{\mathit{phase}} \land
\varphi_{\mathit{stride}} \land \varphi_{\mathit{perm}}$.
\end{theorem}

\noindent
A compiled, axiom-audited Lean~4 development records this theorem; see Section~\ref{sec:lean}.

\paragraph{Stride theory convexity.}
Nelson--Oppen combination requires convexity (or completeness of
equality propagation) for stably-infinite theories.  $\Tstride$
operates in QF\_LIA over $\mathbb{Z}_{\geq 1}$, which is convex
by Lassez--Maher--Marriott~\cite{lassez88}: any disjunction of
equalities implied by a QF\_LIA formula is witnessed by at least
one disjunct.  The NIA fragment arising from reshape constraints
uses a semi-linear subfragment (at most one symbolic factor per
product), preserving convexity in practice.

concretising symbolic dimensions through constraint propagation,
whereas \tguard{}'s current QF\_LIA encoding does not track
non-linear relationships between symbolic sizes.  Extending the
stride or permutation theories to encode such path-sensitive
constraints is a clear direction for future work.

\paragraph{New capabilities.}

exercised by the earlier synthetic suite:
\begin{itemize}[leftmargin=1.5em,nosep]
  \item \textbf{Dynamic shape inference}: correct handling of
    \texttt{-1} dimensions in \texttt{view} and \texttt{reshape},
    where the unknown extent is inferred from the product-equality
    constraint $\prod s_i = \prod d_j$.
  \item \textbf{Einsum support}: verification of Einstein summation
    index strings, including implicit broadcasting and contraction
    over repeated indices.
  \item \textbf{Broadcast analysis}: multi-operand broadcasting
    following NumPy semantics, with symbolic dimension alignment
    checked via Z3.
\end{itemize}

\paragraph{Comparison with PyTEA.}
PyTEA reports precision~0.95 and recall~0.89 on its own regression
suite by concretising symbolic dimensions to small constants.
\tguard{}'s lower recall (0.714 vs.\ 0.89) reflects the cost of
fully parametric verification: we prove safety for \emph{all}
dimension values rather than checking a finite sample.  In
exchange, \tguard{} provides formal safety certificates and
catches multi-theory bugs (device, phase) that PyTEA does not
model.  The two tools are complementary: PyTEA excels at
single-theory symbolic shape reasoning, while \tguard{} covers the
cross-cutting property space.

\section{Empirical Rigor: Ablations, Robustness, Reproducibility}
\label{sec:rigor}

Beyond raw precision/recall, a verifier that aspires to be trusted in a PyTorch
workflow must answer four further questions: \emph{which} parts of the design
earn their keep, whether the headline numbers survive a held-out split and
multiple-comparison correction, whether verdicts are stable across the torch and
Python versions users actually run, and whether everything regenerates from one
command. Every number in this section is produced by a deterministic harness
under \texttt{reproducibility/} with a pinned seed and a \texttt{-{}-check} mode
that fails CI on drift.

\subsection{Domain ablation: every domain is necessary}\label{sec:ablation-domain}
\tguard{}'s five-theory product (shape, dtype, device, gradient, phase) is
ablated by a leave-one-domain-out (LODO) study over a stratified corpus of
$n=300$ cases (60 per domain; seed \texttt{20240604},
\texttt{reproducibility/domain\_ablation.py}). For each of the four
\emph{verification} domains, full-product recall on its bug class is $1.0$ while
LODO recall collapses to $0$---i.e.\ the marginal contribution of every domain is
exactly $1.0$ and no other domain compensates for a missing one (the recall
matrix is diagonal). The phase domain is confirmed \emph{diagnostic-only}: it
registers train/eval well-formedness but refutes nothing (recall $0.0$ on its own
``class''), and we report it as such rather than overclaiming. The domains are
therefore empirically orthogonal and each is independently necessary.

\subsection{CEGAR refinement-depth ablation}\label{sec:ablation-cegar}
Sweeping the predicate-refinement budget from depth $0$ to $6$ over 16 conflict
and 8 clean cases (\texttt{reproducibility/cegar\_depth\_ablation.py}) shows the
intended profile: recall is \emph{depth-invariant} (all 16 conflicts detected
even at depth $0$), while \emph{precision} rises from depth $0$ and reaches its
knee at depth $1$, where the number of refined-contract diagnoses jumps from $0$
to $16$ and then plateaus. The loop saturates at $40$ total iterations, well
within the Lean-proved bound of Section~\ref{sec:lean}. Depth~$1$ is thus the
cost/precision sweet spot, and refinement buys \emph{diagnosis quality}, not
recall.

\subsection{Pre-registered blind split and statistical correction}
\label{sec:blind}
To rule out tuning-set overfitting we froze a held-out split of $186$ cases
($138$ buggy, $48$ clean), disjoint from the development set, and pre-registered
its SHA-256 manifest. The observed manifest hash matches the registered one
(\texttt{df881a\dots}), and on the blind split both \texttt{sound} and
\texttt{balanced} modes confirm all three pre-registered hypotheses: H1 (no false
positive: zero clean models flagged), H2 (recall floor $\ge 0.9$ met), and H3 (no
overfitting gap: dev$-$blind recall gap $\le 0.1$)
(\texttt{reproducibility/blind\_split\_eval.py}). Every comparative claim against
a baseline additionally carries an effect size and a multiple-comparison
correction: over a family of four McNemar comparisons, Holm and
Benjamini--Hochberg agree on the set of significant results
(\texttt{reproducibility/effect\_sizes.py}), so the headline advantages are not
artifacts of uncorrected multiplicity.

\subsection{Cross-version and cross-interpreter robustness}\label{sec:robust}
Because the analyzer is \emph{static} and never executes the model, its verdict
should not depend on the installed torch build. We confirm this directly: across
the torch $2.1.0$ through $2.9.1$ wheel matrix (nine versions), the verdict on a
$227$-case corpus is byte-identical to a pinned baseline digest
(\texttt{reproducibility/cross\_version\_stability.py}). Verdicts are likewise
invariant under Python hash-seed randomization---a single distinct verdict digest
across randomized runs and the supported Python $3.9$--$3.14$ matrix
(\texttt{reproducibility/cross\_python\_determinism.py})---so results are
reproducible bit-for-bit regardless of interpreter.

\subsection{Scaling}\label{sec:scaling}
End-to-end wall-clock on synthetic models of growing depth (width $32$, three
reps per size) scales \emph{polynomially, not exponentially}: a log--log fit of
median latency versus depth has exponent $1.69$ with $R^2=0.988$

latency grows from $12$\,ms at depth $1$ to $4.3$\,s at depth $64$
(Table~\ref{tab:scaling}), comfortably within an interactive budget for the model

\section{Lean~4 Mechanization}\label{sec:lean}

The repository ships a \emph{compiled}, \texttt{sorry}-free Lean~4
formalization (pinned \texttt{lean-toolchain} \texttt{v4.14.0},
\texttt{lakefile.lean}, \texttt{lake build} green) comprising 18 modules,
$\sim$3{,}800 lines and 210 theorems/lemmas. Soundness is not asserted by
inspection: \texttt{TensorGuard/AxiomAudit.lean} runs \texttt{\#print axioms}
on the headline results, and---crucially---\texttt{tests/test\_lean\_whole\_%
pipeline\_audit.py} makes the audit \emph{total and drift-proof}: it
auto-discovers \emph{every one} of the library's 210 public theorems, elaborates
a \texttt{\#print axioms} for each through the Lean kernel, and asserts each
depends only on the trusted kernel set $\{\texttt{propext},
\texttt{Classical.choice}, \texttt{Quot.sound}\}$ and \emph{never} on
\texttt{sorryAx}. A new theorem hiding a \texttt{sorry} or an exotic axiom is
caught automatically, with no hand-maintained list---the machine-checked witness
behind the ``sorry-free'' claim.

The mechanization covers six components:

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Operator transfer-function soundness.} Per-operator rules for
    the shape DSL (\texttt{linear}, \texttt{view}, \texttt{broadcast\_add},
    \texttt{matmul}, \texttt{transpose}, \texttt{permute}, \texttt{sum},
    cross-entropy, argmax, \dots) are proved sound against a denotational
    reference (\texttt{Soundness.lean}, \texttt{Extended.lean},
    \texttt{V5OperatorRules.lean}, \texttt{MatmulSound.lean}).

  \item \textbf{Reduced-product abstraction.}
    \texttt{ReducedProduct.lean} proves the product transfer functions are
    reductive and monotone, the meet is a component-wise lower bound, and the
    $\gamma$-concretization is sound (the reduction preserves concretization)---
    the formal core of the five-theory product domain.

  \item \textbf{CEGAR termination and a tight bound.}
    \texttt{CegarBound.lean} mechanizes that the predicate-refinement loop
    terminates inside a finite predicate universe and obeys
    $\mathit{iterations} \le 1 + |\mathit{discovered\ predicates}|$, matching
    the measured harness one-to-two orders of magnitude below the naive bound.

  \item \textbf{Known-unsoundness boundary, made precise.} The two documented
    gaps are formalized rather than hidden: \textbf{U2} (SAFE-on-infeasible) is
    \emph{closed} by a Lean-checked fix that abstains on infeasible refinements
    (\texttt{CegarInfeasible.lean}), and \textbf{U1} (the verifiable-fragment
    boundary) is proved \emph{mode-dependent}---\texttt{sound} mode abstains on
    every fragment violation and is sound, while the permissive modes' recall
    trade-off is made exact (\texttt{FragmentModes.lean}).

  \item \textbf{Non-shape transfer functions (this work).}
    \texttt{DeviceDtype.lean} models the four scalar algebras the verifier runs
    alongside shape---device, element dtype, training phase and gradient
    flow---each a finite lattice with a distinguished $\top$ (\texttt{unknown})
    element, exactly as \texttt{model\_checker.py} implements them. For every
    algebra we prove the two properties the engine relies on: \emph{no false
    positive} (an \texttt{unknown} operand never flags) and \emph{refutation
    soundness} (a flagged bug witnesses a genuine PyTorch runtime error over
    every concretization), plus the structural laws the frontends depend on
    (device-move round-trips, \texttt{pin\_memory} preservation, dtype
    elementwise promotion is total/commutative/never-flags, \texttt{detach}
    zeroes the gradient bit). Both guarantees \emph{lift to the reduced
    product}: it flags iff some component flags, and inherits no-false-positive
    and refutation soundness.

  \item \textbf{SMT-encoding faithfulness and end-to-end auditing (this work).}
    The previous component proves the \emph{abstract} algebras sound; this one
    closes the gap to the \emph{concrete} constraints the solver discharges and
    to the rest of the pipeline. \texttt{SmtEncoding.lean} models the
    enumeration-sort equality constraint the verifier hands Z3 for every
    device/phase/gradient check (\texttt{encode\_device\_constraint},
    \texttt{encode\_phase\_constraint},
    \texttt{encode\_gradient\_constraint}) and proves it \emph{faithful}: the
    pinned same-value formula is satisfiable iff the two endpoints are equal, so
    the solver's UNSAT verdict---a reported mismatch---holds iff the endpoints
    genuinely differ, and coincides exactly with the abstract \texttt{*Bug}
    predicate of the previous component (\texttt{device\_smt\_matches\_devBug}).
    \texttt{CrossDomain.lean} does the same for the
    \texttt{encode\_cross\_domain\_constraint} encoder, proving a device-transfer
    op preserves shape exactly while leaving the device free, and a non-transfer
    op preserves device exactly while leaving shape free. The dtype promotion
    join is strengthened to a fully proved semilattice (associative,
    unknown-absorbing), justifying the order-independent never-flagging
    elementwise transfer, and \texttt{GradFlow.lean} lifts the single-op
    \texttt{detach} check to the gradient-flow transfer over an entire chain of
    ops, proving it compositional with absorbing resets. These results narrow the
    trusted computing base: the previously-trusted faithfulness of the device,
    phase and gradient enum encodings is now \emph{proved}.
\end{enumerate}

\caption{Machine-checked soundness modules added in this work (all
\texttt{sorry}-free, \texttt{propext}-only, each gated by a Python conformance
test against real code).}
\label{tab:lean-new}
\begin{tabular}{@{}llp{4.3cm}@{}}
\toprule
Lean module & Cross-check & Guarantee \\
\midrule

\texttt{SmtEncoding.lean}  & real Z3 & device/phase/grad enum encoding UNSAT $\Leftrightarrow$ endpoints differ \\

\paragraph{Conformance: proofs cross-checked against real code.}
Each soundness module is paired with a Python test that mirrors the Lean
\emph{decision} function and asserts the \emph{live} system reproduces its
predictions on real artifacts---not merely on a Lean-internal model. For the
non-shape transfer functions, \texttt{tests/test\_device\_dtype\_transfer.py}
mirrors every Lean \texttt{*Bug} predicate and checks that
\texttt{verify\_module}'s \texttt{device\_mismatch}/\texttt{dtype\_error}/%
\texttt{phase\_error}/\texttt{gradient\_broken} verdicts match on consistent,
mismatching and unknown-operand probes for all four algebras, with the
consistent cases additionally executed against real torch. The faithfulness
modules go one level deeper and exercise the \emph{actual solver and dispatcher}:
\texttt{test\_smt\_encoding\_faithful.py} and
\texttt{test\_cross\_domain\_encoding.py} run the real \texttt{\_Z3Context}
encoders through Z3 on every concrete device/phase/gradient and shape endpoint
pair and assert the live SAT/UNSAT verdict equals the Lean prediction;
\texttt{test\_grad\_flow\_transfer.py} replays every gradient-flow chain of length
$\le 3$ on a real autograd tensor and asserts \texttt{out.requires\_grad} equals
the proved \texttt{gradRun}; and \texttt{test\_dtype\_promotion\_lattice.py}
executes real \texttt{torch.add} on every promotable dtype pair to validate the
``elementwise dtype never flags'' law. This narrows the conformance gap from
``tested'' to ``the proved predictions are observed to hold on real PyTorch and
real Z3.''

\paragraph{Trusted computing base (TCB).}
The mechanization does \emph{not} cover completeness of verification
(undecidable in general by Rice's theorem~\cite{rice53}), Z3's internal
decision procedures, or full bit-level faithfulness of all 142 operator
transfer functions to PyTorch (the conformance gap, mitigated by the
cross-checks and property-based testing above). It \emph{does} now cover the
faithfulness of the device, phase and gradient enumeration encodings the solver
runs---previously trusted, now proved (\texttt{SmtEncoding.lean},
\texttt{CrossDomain.lean})---so the remaining encoding-trust surface is confined
to the linear-arithmetic shape constraints and Z3's own soundness.

\section{Related Work}\label{sec:related}

\paragraph{Type-based shape checking.}
jaxtyping~\cite{jaxtyping} provides runtime shape annotations
for JAX/PyTorch using Python type hints; it requires manual
annotation and catches errors only at execution time.
tsanley~\cite{tsanley} infers named dimensions from runtime
traces but does not verify them statically.  Neither tool
reasons about device placement, training phase, or cross-cutting
property interactions.

\paragraph{Static shape analysis.}
PyTEA~\cite{pytea} performs static type analysis for PyTorch
tensor shapes via abstract interpretation.  It targets individual
operations and does not reason about device placement, training
phase, or architecture-level composition via SMT theory
combination.  TensorFlow's shape inference operates
at graph construction time but is limited to the TensorFlow
computation model.  No existing static shape analyzer verifies
the cross-cutting property interactions that \tguard{} targets
(Section~\ref{sec:cross-cutting}).

\paragraph{SMT-based program verification.}
Dafny~\cite{leino10} and F*~\cite{fstar} use SMT solvers for
general program verification with refinement types.
Viper~\cite{muller16} provides verification infrastructure for
permission-based reasoning.  \tguard{} applies similar SMT-based
techniques but specializes them with domain-specific tensor shape
theories and UserPropagator plugins.

\paragraph{Refinement types.}
Liquid Types~\cite{flanagan06} pioneered practical refinement
type checking via SMT, inferring refinement types automatically
using predicate abstraction.  RefinedC~\cite{refinedc} extends
refinement types to C with ownership semantics.  \tguard{} adapts
the refinement type paradigm to tensor shape verification with
domain-specific theories.

\paragraph{Abstract interpretation for neural networks.}
Singh et al.~\cite{singh19} develop abstract domains for
certifying neural network properties (robustness, fairness).
Their work targets network \emph{behavior} rather than
\emph{structural} shape safety, and operates on trained models
rather than source code.

\section{End-to-End Walkthrough and Operator Coverage}\label{sec:walkthrough}

\paragraph{A worked example.} Figure-style, consider the 22-line model below
(shipped as \texttt{examples/shape\_bug.py}): a \texttt{Conv2d(3,128,\dots)}
followed by \texttt{AdaptiveAvgPool2d(1)} and \texttt{flatten(1)} produces a
$[B,128]$ activation, but the head is declared \texttt{Linear(256,10)}.

\begin{verbatim}
self.conv = nn.Conv2d(3, 128, 3, padding=1)
self.pool = nn.AdaptiveAvgPool2d(1)
self.fc   = nn.Linear(256, 10)   # BUG: expects 256, gets 128
def forward(self, x):
    x = self.conv(x)             # [B, 128, H, W]
    x = self.pool(x).flatten(1)  # [B, 128]
    return self.fc(x)            # mismatch
\end{verbatim}

\noindent Running \texttt{tensorguard analyze examples/shape\_bug.py} terminates

\begin{verbatim}
{ "id": "shape-22", "severity": "error",
  "category": "shape-error",
  "message": "Linear layer expects input dim 256, got 128",
  "location": { "line": 22, "column": 12 } }

\section{Threats to Validity}\label{sec:threats}

\paragraph{Internal validity.} The headline recall/precision could in principle
reflect tuning to the development corpus. We mitigate this with the
pre-registered blind split of Section~\ref{sec:blind} (manifest hash fixed before
evaluation; H1--H3 confirmed on held-out data) and with multiple-comparison
correction on every comparative claim. The abstention accounting is explicit:
\texttt{sound} mode converts every out-of-fragment construct into
\texttt{UNKNOWN} rather than a silent verdict, so a missed bug surfaces as an
abstention rather than an unsound \texttt{SAFE}.

\paragraph{Construct validity.} The strongest threat is the \emph{conformance
gap}: a transfer function could mis-model PyTorch and the proofs would faithfully
certify the wrong semantics. This is precisely why the Lean soundness modules are
each paired with a test that runs the \emph{live} verifier, real Z3, and the real
torch dispatcher (Section~\ref{sec:lean}); the remaining gap is the per-operator
bit-level faithfulness of the shape transfer functions, bounded by property-based
differential testing against the live dispatcher.

\paragraph{External validity.} Results may not transfer to model families outside
the corpus. The corpus is stratified by bug class and drawn from real public
repositories, the false-positive stress corpus uses clean real models, and the
cross-version/cross-interpreter matrices (Section~\ref{sec:robust}) show the
verdict is invariant to the torch and Python versions a practitioner runs. The
phase domain is reported as diagnostic-only to avoid overclaiming.

\paragraph{Reproducibility.} Wall-clock numbers are machine-dependent and are
regenerated but not byte-compared; all categorical verdicts are content-addressed
and reproduce bit-for-bit under the pinned capsule (Section~\ref{sec:capsule}).

\section{Conclusion}\label{sec:conclusion}

We have presented \tguard{}, a static multi-property verifier for
PyTorch that combines five domain-specific SMT theories---shape,
device, phase, stride, and permutation---to catch cross-cutting
bugs that no existing tool detects.  On a 52-model benchmark of
multi-theory bugs sourced from real-world issues (HuggingFace
\#13666, torchvision ResNet, detectron2, YOLOv5, mmdetection),
\tguard{} achieves F1 = 0.625 with perfect precision. The baseline
rows in this comparison should be read as capability lower bounds,
not full per-case reruns: TorchScript, mypy, jaxtyping, and PyTEA
lack the device/phase reasoning that defines these cross-cutting
bug classes. The tool supports 142 operator transfer functions,
covers real-world architectures (ResNet, VGG, MobileNetV2,
EfficientNet, DenseNet), and produces parametric safety
certificates via IC3/PDR over symbolic dimensions. The repository
also includes a compiled, \texttt{sorry}-free Lean~4 formalization
($\sim$3{,}800 lines, 210 theorems/lemmas, \emph{all} machine-audited to
trusted kernel axioms) covering the operator transfer functions, the
reduced-product abstraction, CEGAR termination, the two known-unsoundness gaps,
the device/dtype/phase/gradient transfer functions, and the faithfulness of the
Z3 encoding the solver runs.

The primary limitation is the conformance gap between the
mechanized specification and the Python implementation.
The remaining false negatives on cross-cutting benchmarks
(Recall = 0.455) stem from device-only bugs where shapes match
perfectly; extending the device theory to track cross-device
operations through \texttt{@} and \texttt{expand} is future work.
Additional directions include closing the conformance gap via
verified extraction, extending the operator registry toward full
PyTorch coverage, and integrating \tguard{} into CI/CD pipelines
as a pre-merge gate for multi-property safety.

\section{Proof Sketches for Soundness Conjectures}\label{app:proofs}

\subsection{Type Soundness (Conjecture~\ref{conj:soundness})}

\begin{proof}[Extended proof sketch]
We proceed by induction on the typing derivation
$\Gamma \vdash e : \tau$.

\textbf{Base case (T-Var):} If $e = x$ and $\Gamma(x) = \tau$,
then $\sigma \models \Gamma$ implies $\sigma(x) \models \tau$
by definition.

\textbf{Inductive case (T-Linear):} Assume
$\Gamma \vdash x : \{t \mid \mathit{dim}_{-1}(t) = f_\text{in}\}$.
By the induction hypothesis, $\sigma(x)$ has last dimension
$f_\text{in}$.  The PyTorch \texttt{nn.Linear} documentation
specifies that the output shape is
$\mathit{shape}(x)_{[0:-1]} \mathbin\| [f_\text{out}]$ when the
input's last dimension equals $f_\text{in}$.  Since the precondition
holds, no \texttt{RuntimeError} is raised, and the output satisfies
the postcondition.  The argument is analogous for all other rules.

\textbf{Theory combination:} Cross-theory constraints
(e.g., device compatibility implying shape compatibility) are
sound by Theorem~\ref{thm:combination} (Lean-proved).

\textbf{Gap:} The proof sketch assumes that each transfer function
faithfully models the corresponding PyTorch operator.  This
assumption is not mechanized; it is validated by property-based
testing against the PyTorch runtime.
\end{proof}

\subsection{Stride Theory Convexity}

\begin{proof}[Proof sketch]
$\Tstride$ generates constraints in QF\_LIA over
$\mathbb{Z}_{\geq 1}$.  QF\_LIA is convex: if
$\varphi \models e_1 = e_2 \lor e_3 = e_4$, then
$\varphi \models e_1 = e_2$ or $\varphi \models e_3 = e_4$.
This follows from the fact that the solution set of a
conjunction of linear inequalities over the integers is a
finite union of lattice points in a convex polytope, and
equality disjunctions over such sets reduce to individual
equalities~\cite{lassez88}.

The NIA subfragment arising from reshape constraints uses at
most one symbolic factor per product term, restricting to
a semi-linear fragment where convexity is preserved.  Full
nonlinear arithmetic would break convexity; our restriction
to semi-linear terms avoids this.
\end{proof}


\section{Machine-Checked Faithfulness Theorems}\label{app:faithful}

For reference, we state the central faithfulness and transfer results added in
this work (all \texttt{sorry}-free, depending only on \texttt{propext}). Let
$\mathrm{Sat}(c_a,c_b)$ denote satisfiability of the pinned same-value constraint
the verifier emits, and let $\mathrm{devBug}$, etc., be the abstract algebra
predicates of \texttt{DeviceDtype.lean}.

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Enum-encoding faithfulness} (\texttt{SmtEncoding.lean}):
    $\mathrm{Sat}(c_a,c_b)\iff c_a=c_b$, hence $\lnot\mathrm{Sat}(c_a,c_b)\iff
    c_a\neq c_b$; and for known devices
    $\lnot\mathrm{Sat}(c_a,c_b)\iff \mathrm{devBug}(c_a,c_b)$. The same UNSAT
    characterization holds for the phase sort and the gradient Boolean.
  \item \textbf{Cross-domain faithfulness} (\texttt{CrossDomain.lean}): a
    transfer op's constraint set is satisfiable $\iff$ \texttt{pre}=\texttt{post}
    (shape preserved, device free); a non-transfer op's $\iff$
    $d_{\text{pre}}=d_{\text{post}}$ (device preserved, shape free).
  \item \textbf{Dtype promotion semilattice} (\texttt{DeviceDtype.lean}):
    $\mathrm{dtPromote}$ is commutative, idempotent, associative, and
    $\top$-absorbing; hence the elementwise dtype transfer never flags
    ($\mathrm{dtElementwiseBug}\equiv\texttt{false}$).
  \item \textbf{Gradient-flow chain transfer} (\texttt{GradFlow.lean}):
    $\mathrm{gradRun}$ is compositional
    ($\mathrm{gradRun}\,b\,(xs\!+\!\!+\,ys)=\mathrm{gradRun}\,(\mathrm{gradRun}\,
    b\,xs)\,ys$); \texttt{detach}/\texttt{noGrad} are absorbing; and on the
    reattach-free fragment the outgoing bit is \texttt{true} iff the input
    required grad and no reset intervened.
  \item \textbf{Reduced-product lifting} (\texttt{DeviceDtype.lean}): the product
    over the four scalar algebras flags iff some component flags, and inherits
    both no-false-positive and refutation soundness.
\end{itemize}

Each item is gated by a Python test that reproduces the predicted
SAT/UNSAT/verdict on the \emph{real} solver or the \emph{real} torch dispatcher;
the whole library's 210 theorems are audited \texttt{sorry}-free by
\texttt{test\_lean\_whole\_pipeline\_audit.py}.


\section{Trusted Computing Base Summary}\label{app:tcb}

The trusted computing base (TCB) of \tguard{} comprises the
following components, listed in decreasing order of trust
required:

\begin{enumerate}[leftmargin=2em]
  \item \textbf{Z3 SMT solver.}  We trust Z3's decision
    procedures for QF\_LIA, QF\_NIA, and QF\_UF.  Z3 is
    widely used and extensively tested, but bugs are possible.

  \item \textbf{Lean~4 proofs.}  The Lean~4 formalization is
    compiled (\texttt{lake build}) and \texttt{sorry}-free, and its
    headline soundness results are machine-audited to rest only on the
    trusted Lean kernel axioms. The Lean checker is not invoked at
    \tguard{} runtime, so it constrains the \emph{specification}; the
    conformance gap to the Python implementation is closed test-by-test
    by the live cross-checks (Section~\ref{sec:lean}).

  \item \textbf{Python implementation.}  The \tguard{} Python
    code (graph extraction, transfer functions, constraint
    generation) is \emph{not} mechanically verified.  The
    conformance gap between the Lean specification and the
    Python implementation is mitigated by:
    \begin{itemize}[nosep]
      \item Live cross-checks that assert the verifier reproduces each
        Lean decision function's predictions on real \texttt{nn.Module}s.
      \item Property-based testing (Hypothesis) exercising
        mechanized theorem statements on the implementation.
      \item Extensive unit and integration tests
        (3{,}709 tests total).
      \item Evaluation on real-world models providing
        empirical confidence.
    \end{itemize}

  \item \textbf{Transfer function faithfulness.}  Each of the
    142 transfer functions is assumed to faithfully model the
    corresponding PyTorch operator.  This is validated by
    property-based testing against the PyTorch runtime but
    not mechanically proved.

  \item \textbf{Graph extraction correctness.}  The AST-based
    and FX-based graph extractors are assumed to correctly
    reconstruct the computation graph from source code.
    Dynamic dispatch, monkey-patching, and metaclass magic
    can cause extraction failures (reported as warnings, not
    silent misses).
\end{enumerate}
