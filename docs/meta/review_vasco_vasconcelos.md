# Review: TensorGuard — Static Tensor Shape Verification via SMT Theory Combination

**Reviewer:** Vasco T. Vasconcelos
**Persona:** Probabilistic Models and Formal Methods Expert (Type Theory, Session Types)
**Date:** 2026-03-02

---

## Summary

TensorGuard presents a static verification system for tensor shape compatibility in PyTorch, framed as a combination of refinement type inference and SMT-based model checking. The system encodes tensor shapes as refinement predicates over a 5-theory product domain (Shape × Device × Phase × Stride × Permutation) and verifies `nn.Module` subclasses without programmer annotations. The approach draws on multiple traditions: refinement types from the liquid types literature, theory combination from the SMT community, model checking (IC3/PDR) from the hardware verification community, and CEGAR from the software verification community. The system is accompanied by a 1,587-line Lean 4 mechanization of the theory combination soundness argument.

From a type-theoretic perspective, this work occupies an interesting position at the intersection of refinement types and abstract interpretation. The core idea — that tensor shapes can be expressed as refinement predicates `{v: Tensor | shape(v) == (batch, channels, height, width)}` and that shape errors correspond to refinement subtyping failures — is well-motivated and connects to the broader program of eliminating runtime errors through static type-level reasoning. However, as a researcher working on type theory, session types, and type systems for concurrent/distributed computation, I find the type-theoretic foundations of this work underdeveloped. The paper presents 43 typing rules (mentioned in the project documentation), operator transfer functions, and a bidirectional type checking approach, but does not establish the standard type-theoretic metatheory: progress, preservation, canonical forms, or decidability of type checking. The connection to the refinement types and gradual typing literature is superficial.

The work is strongest as a practical tool contribution and weakest as a type-theoretic contribution. The SMT-based approach effectively bypasses the need for a proper type system by reducing everything to constraint solving — which is pragmatically effective but leaves the type-theoretic questions unanswered. I would recommend the authors either strengthen the type-theoretic foundations or honestly position the work as a domain-specific model checker rather than a type inference system.

## Strengths

1. **The refinement type perspective is insightful and well-chosen.** Encoding tensor shapes as refinement types `{v: Tensor | shape(v) == (d1, ..., dn)}` is a natural fit. The key insight from the `tensor_shapes.py` module — that dimensions can be either concrete integers or symbolic names (`ShapeDim.value: Union[int, str]`) — directly corresponds to the distinction between base types (concrete) and type variables (symbolic) in polymorphic type systems. The propagation of symbolic dimensions through operations is analogous to type variable unification in Hindley-Milner inference. The predicate template language (DIM_EQ, DIM_GT, DIM_GE, DIM_DIVISIBLE, DIM_MATCH) in the CEGAR module is essentially a refinement logic restricted to a decidable fragment, which aligns with the liquid types approach of Rondon, Kawaguchi, and Jhala (PLDI 2008). The authors' observation that "runtime guards in dynamically-typed languages provide a natural and abundant source of predicate templates" echoes the liquid types insight that program-level predicates can seed refinement inference.

2. **The 5-theory product domain has a clean algebraic structure.** The decomposition into Shape (ℤ≥1), Device ({CPU, CUDA:0–3}), Phase ({TRAIN, EVAL}), Stride (multiplicative layout), and Permutation (axis reordering) has a product-domain flavor that is reminiscent of reduced product domains in abstract interpretation (Cousot & Cousot, 1979). Each theory has its own sort, function symbols, and axioms, and the theories interact only through shared variables. From a type-theoretic perspective, this corresponds to a dependent product where each component tracks a different aspect of the tensor type. The formal axiomatization of each theory (e.g., the broadcast theory with axioms A1–A6, the stride theory with axioms A1–A3) is clean and follows the SMT-LIB style. The Lean 4 mechanization that proves these theories can be soundly combined via Tinelli-Zarba is a meaningful contribution to the type-theoretic foundations.

3. **The connection between UserPropagators and type-checking judgments is interesting.** Each Z3 UserPropagator implements what is essentially a type-checking rule: given input types (shapes), check compatibility and compute output types (shapes). The `fixed` callback corresponds to the synthesis (inference) direction of bidirectional type checking — when input dimensions are known, propagate output dimensions. The `final` callback corresponds to the checking direction — verify that all constraints are satisfied. This connection is not explicitly drawn in the paper but is implicit in the architecture. The broadcast theory's decision procedure (axioms A1–A6 with eager propagation) can be viewed as a decidable checking rule for broadcast types.

4. **The Lean 4 mechanization of broadcast soundness and completeness is non-trivial.** The `broadcastDim_sound` and `broadcastDim_complete` theorems establish bidirectional equivalence between the Boolean checker and the semantic specification, which is the type-theoretic analogue of proving that type checking is both sound (well-typed programs satisfy the semantic property) and complete (all semantically valid programs are accepted by the type checker). The broadcast associativity proof (`broadcast_assoc_ext`) and the pairwise compatibility preservation lemma (`broadcast_pairwise_preserved`) establish algebraic properties that are essential for the compositionality of the type system — they guarantee that multi-operand broadcasting can be checked incrementally without losing precision.

5. **The separation of symbolic and concrete dimensions is type-theoretically principled.** The `ShapeDim` type with `Union[int, str]` implements a restricted form of dependent types where dimensions can be either concrete values or universally quantified variables. This is a clean design that avoids the full complexity of dependent types (no dependent functions, no sigma types, no universe hierarchy) while capturing the specific form of parametric polymorphism needed for tensor operations. The IC3/PDR engine that proves safety for "all values of symbolic dimensions" is essentially performing universal quantifier elimination — proving ∀ batch_size ∈ ℤ≥1. safe(model, batch_size) — which is the correct metatheoretic statement for parametric safety.

6. **The CEGAR loop has a type-inference flavor.** The iterative predicate discovery — verify, find counterexample, extract predicate, refine — resembles the iterative constraint generation and solving in Liquid Type inference. In both systems, the verifier generates constraints from the program, checks them against a background theory, and refines the type environment when constraints are insufficient. The backward trace from failing step to input shape assumptions is analogous to computing weakest preconditions, which is how Liquid Types propagate refinements backwards through the program. This connection could be made more explicit and would strengthen the type-theoretic positioning of the work.

7. **The decidability characterization is type-theoretically relevant.** The result that 94.9% of operators produce QF_LIA constraints (decidable in polynomial time) while 6 operators produce NP-hard constraints is analogous to showing that type checking is decidable for a restricted fragment of the type system. This is important for practical type systems — decidability ensures that the type checker always terminates. The identification of reshape/flatten as the complexity bottleneck (entering QF_NIA) corresponds to identifying which typing rules introduce undecidability, which is a standard question in type theory (e.g., type checking for System F is undecidable, but type checking for simply-typed lambda calculus is decidable).

## Weaknesses

1. **No formal type system is presented.** Despite the project title referencing "Refinement Type Inference" and the documentation mentioning 43 typing rules, the paper does not present a formal type system in the traditional sense. There is no grammar of types, no typing judgments (Γ ⊢ e : τ), no subtyping relation (τ₁ <: τ₂), and no formal statement of progress or preservation. The `approach.json` file contains a sketch of the type system with base types, refinement types, and dependent function types, but this is not developed into a formal system with explicit rules and metatheorems. Instead, the "type system" is implicitly defined by the SMT encoding — types are Z3 formulas, type checking is SAT/UNSAT checking, and type inference is constraint propagation. This is pragmatically effective but type-theoretically unsatisfying. A proper formalization would define: (a) a syntax of shape types, (b) typing rules for each of the 117 operators, (c) a subtyping relation based on logical entailment of refinement predicates, and (d) proofs of progress and preservation.

2. **The bidirectional type checking claim is not substantiated.** The documentation mentions bidirectional type checking, and the architecture has inference-like (forward propagation from inputs to outputs) and checking-like (backward constraint propagation from consumers to producers) components. However, bidirectional type checking in the sense of Pierce and Turner (2000) — with mode annotations on typing rules (⇒ for synthesis, ⇐ for checking) and a well-defined mode discipline — is not formalized. The forward/backward propagation in the model checker is an ad hoc approximation that does not guarantee the properties that bidirectional type checking provides (e.g., principal types, decidability, mode correctness). The claim should either be formalized or retracted.

3. **The relationship to refinement types and Liquid Types is underexplored.** The paper positions itself in the refinement types tradition but does not engage deeply with the relevant literature. Liquid Types (Rondon et al., PLDI 2008) infer refinement types by solving Horn clause constraints. The key insight is that the set of predicates is fixed (drawn from program-level qualifiers), and inference reduces to solving a system of implications ∀x. p₁(x) ∧ ... ∧ pₖ(x) ⟹ q(x) where q ranges over the qualifier set. TensorGuard's CEGAR loop is similar but differs in that predicates are *discovered* iteratively rather than drawn from a fixed set. This is closer to the CounterExample-Guided Abstraction Refinement of Predicate Abstraction (CEGAR-PA, Ball et al., 2001) than to Liquid Types. The paper should clarify this distinction and discuss whether TensorGuard's predicate discovery can be reformulated as a Liquid Type inference problem (e.g., by extracting all possible shape predicates from the model and solving the corresponding Horn clause system in one shot).

4. **Progress and preservation are not addressed.** The standard metatheoretic properties for a type system are: (a) Progress: if Γ ⊢ e : τ and e is not a value, then e can take a step (no stuck states); (b) Preservation (Subject Reduction): if Γ ⊢ e : τ and e →* e', then Γ ⊢ e' : τ (types are preserved by reduction). For TensorGuard, the analogue would be: (a) if the verifier says "safe," then every forward pass of the model succeeds without shape errors (progress); (b) the shape type of each intermediate tensor is preserved through each computation step (preservation). The soundness of the Z3 encoding provides a partial guarantee, but the gap between the SMT model and the actual PyTorch execution semantics is not formally characterized. A shape error in the SMT model corresponds to UNSAT; but does SAT in the SMT model guarantee that the corresponding PyTorch operations succeed? This depends on the faithfulness of the 117 operator transfer functions, which is assumed but not proven.

5. **The product domain lacks inter-theory reduction.** In abstract interpretation, a reduced product domain uses inter-domain communication to improve precision beyond what each component domain provides independently. For example, learning that `device == CUDA:0` might constrain the set of valid operations (some operators are CPU-only), which in turn constrains shapes. TensorGuard's 5 theories interact only through shared variables in the Tinelli-Zarba combination — there is no inter-theory reduction. This means the product domain is a *direct product* rather than a *reduced product*, and precision is lost. For example: the Phase theory knows that `self.training == False` (eval mode), and the Shape theory knows that dropout is a no-op in eval mode. But if the two theories don't communicate this, the verifier might analyze both branches of an `if self.training:` conditional unnecessarily. The path-sensitive analysis with `OpKind.CONDITIONAL` handles this case operationally, but it is not formalized as an inter-theory reduction.

6. **The connection to gradual typing is missed.** The treatment of unsupported operators as identity (shape-preserving) is essentially a form of gradual typing: known operators have precise shape types, while unknown operators have the imprecise type `?` (the dynamic type). In gradual typing (Siek & Taha, 2006), the dynamic type `?` is consistent with any type — it never causes a static type error. TensorGuard's identity assumption is similar: an unknown operator produces the same shape as its input, which is consistent with any downstream consumer's shape expectations. However, this consistency is *wrong* when the unknown operator actually changes the shape, leading to missed errors. The gradual typing literature has developed the concept of *blame* to identify which imprecise type annotation is responsible for a runtime error. TensorGuard should adopt a similar approach: when an unsupported operator is encountered, tag the output shape as "imprecise" and propagate this imprecision through the computation graph. If the verification ultimately relies on an imprecise shape at a critical point, report this as a low-confidence verdict rather than a definitive "safe."

7. **The 43 typing rules are not presented or analyzed.** The project documentation references 43 typing rules, but these are not listed, formally stated, or analyzed for coherence. For a type system to be well-defined, the typing rules must be: (a) syntax-directed (or at least amenable to algorithmic checking), (b) deterministic (or at least canonical — principal types exist), (c) sound (well-typed programs don't go wrong), and (d) complete (or at least characterize what is missed). Without seeing the 43 rules, I cannot assess whether they form a coherent type system or are simply 43 ad hoc operator-specific shape transformation functions. If the latter, the work should not claim to be a "type system" but rather a "shape analysis" or "shape checker." The distinction matters: a type system provides compositional guarantees (each module can be checked independently), while a shape checker may require whole-program analysis.

## Minor Issues

- The `approach.json` file defines refinement types as `{x : τ | φ}` where φ ∈ P, with a coNP-complete subtyping problem. But the SMT encoding uses Z3, which solves SAT (NP), not coSAT (coNP). The subtyping check `∀x. φ₁(x) → φ₂(x)` is checked as `¬∃x. φ₁(x) ∧ ¬φ₂(x)`, i.e., UNSAT checking. This is correct but should be stated explicitly.
- The typing rules for `torch.cat` (concatenation along a dimension) and `torch.stack` (adding a new dimension) are among the most error-prone in practice. How are these formalized? Do the typing rules handle dimension-indexed operations correctly (e.g., `torch.cat([a, b], dim=1)` where `a.shape[1] + b.shape[1]` gives the output)?
- The `denotational_semantics.py` module exists in the source tree but is not discussed. Does this provide a denotational semantics for the shape type system? If so, this would significantly strengthen the type-theoretic foundations.
- The `liquid.py` module is titled "Tensor Shape Verification via Liquid Types" — this suggests a direct connection to the Liquid Types framework. How does this module relate to the main `model_checker.py` verification engine? Are there two parallel verification approaches?
- The `types.py` and `types_extended.py` modules exist but are not described. Do these define a proper type grammar?
- The composition soundness module (`composition_soundness.py`) and its tests suggest that the authors have thought about compositional verification. Does this provide a form of assume-guarantee reasoning for sub-modules?
- The `knuth_bendix.py` module for constraint normalization is interesting — Knuth-Bendix completion for term rewriting could be used to normalize shape expressions before SMT solving. But is this related to type normal forms in type theory?

## Questions for Authors

1. **On the type system formalization:** Can you present the 43 typing rules as formal inference rules in the standard notation (premises over conclusion with a horizontal line)? Specifically, I would like to see the rules for: (a) `nn.Linear` (the simplest shape-changing layer), (b) `torch.cat` (which introduces an additive constraint on one dimension), (c) broadcasting (which introduces a max constraint), and (d) `reshape`/`view` (which introduces multiplicative constraints). Are these rules syntax-directed? Do they admit principal types?

2. **On progress and preservation:** Can you state and prove a soundness theorem of the form: "If `verify_model(source, input_shapes)` returns `safe`, then for all concrete instantiations of symbolic dimensions satisfying the discovered shape predicates, the forward pass of the model executes without raising `RuntimeError` due to shape mismatch"? This would be the operational soundness guarantee that connects the static analysis to the dynamic semantics.

3. **On the relationship to session types:** Tensor shape checking in a sequential computation graph is similar to session type checking in a communication protocol: each step has preconditions (input shapes) and postconditions (output shapes), and the composition of steps must type-check end-to-end. Have you considered formalizing the computation graph as a session type, where each step is a communication action and the graph is a protocol? This would provide a clean compositional framework and connect to the well-studied metatheory of session types.

4. **On gradual typing for unsupported operators:** Instead of the identity assumption (which is unsound), would it be possible to introduce a "dynamic shape" type `?_shape` for unsupported operators, analogous to the dynamic type `?` in gradual typing? Concretely: an unsupported operator would produce a tensor with shape `?_shape`, and any downstream operation consuming `?_shape` would succeed statically (consistent with any shape) but emit a warning about imprecise verification. This would make the tool sound (no false negatives from unsupported operators) at the cost of completeness (more unknowns).

5. **On the Liquid Types connection:** Your CEGAR-based predicate discovery iteratively adds predicates to the shape environment. In Liquid Types, the set of predicates (qualifiers) is fixed upfront, and inference is a single-shot Horn clause solving problem. Have you considered extracting all possible shape predicates from the `nn.Module` upfront (e.g., from layer definitions, reshape arguments, and constructor parameters) and solving the Liquid Type inference problem in one pass? This would give convergence guarantees (the qualifier set is finite) and connect your work more directly to the Liquid Types literature.

## Recommendation

**Borderline Accept.** The work addresses a genuine problem (tensor shape errors are the most common ML runtime errors) with a technically interesting approach (SMT-based verification with theory combination). The Lean 4 mechanization and the practical tool engineering are commendable. However, the type-theoretic foundations are underdeveloped: no formal type system is presented, progress/preservation are not addressed, the relationship to refinement types and gradual typing is superficial, and the 43 typing rules are not analyzed for coherence. I would strengthen my recommendation to Accept if the authors: (1) present at least the core typing rules as formal inference rules, (2) state and sketch a proof of operational soundness (progress), (3) clarify the relationship to Liquid Types (is the CEGAR loop an instance of Liquid Type inference or something different?), and (4) address the unsupported-operator problem through a gradual typing lens rather than the unsound identity assumption.

**Confidence:** 3/5
