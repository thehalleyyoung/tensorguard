# TensorGuard formalization: refinement types and the five-theory product domain

> Step 86 deliverable. This document gives the formal specification that backs
> the tool paper. It is **reconciled against the implementation**: every
> algebraic law stated here is checked against the real code in
> `tests/test_formalization.py` (lattice laws on `src/domains/`, widening
> termination, and the soundness side-conditions of the shape theory).

## 1. Programs and the analysed fragment

TensorGuard analyses a `torch.nn.Module` subclass statically, from source. The
analysed **fragment** is the body of `forward` (and helpers it calls) restricted
to: layer applications, tensor algebra (`matmul`, `+`, broadcasting), shape
operations (`reshape`/`view`/`flatten`/`transpose`/`permute`/`cat`/`split`),
reductions, normalisations and attention, and straight-line/branching control
flow whose join is handled by the abstract interpreter. Constructs outside the
fragment cause the analyser to **abstain** (report `ABSTAIN`/"could not prove")
rather than to assume — this is the central design rule that makes `SAFE` sound.

## 2. Tensor refinement types (the five theories)

A **tensor refinement type** is

    τ  ::=  Tensor⟨ s ; d ; e ; φ ; g ⟩

where the five orthogonal *theories* are:

| Theory | Component | Domain |
| --- | --- | --- |
| **Shape** | `s = (δ₁, …, δₙ)` | each `δᵢ` is a *symbolic dimension term* |
| **Device** | `d` | `{cpu, cuda:k, meta, …} ∪ {⊤}` |
| **Dtype** | `e` | `{float32, float16, bfloat16, int64, …} ∪ {⊤}` |
| **Phase** | `φ` | `{train, eval, ⊤}` |
| **Gradient** | `g` | `{requires_grad, no_grad, ⊤}` |

A symbolic dimension term `δ` is generated by

    δ  ::=  n            (concrete, n ∈ ℕ)
         |  x            (symbolic name, e.g. batch, seq_len)
         |  δ ⊕ δ        (⊕ ∈ {+, −, ·, //})

implemented by `ShapeDim` and `SymbolicDimension` in `src/tensor_shapes.py`.
Dimension terms form a commutative structure under `+` and `·` and are reified
into the SMT theory of (nonlinear) integer arithmetic for discharge.

### 2.1 Typing judgements (shape theory)

Judgements have the form `Γ ⊢ x : τ`, read "under environment Γ, value `x` has
tensor type τ". A representative rule for `nn.Linear(in, out)` applied to `x`:

```
        Γ ⊢ x : Tensor⟨ (…, k) ; d ; e ; φ ; g ⟩      ⊨  k = in
        ─────────────────────────────────────────────────────────  (T-Linear)
        Γ ⊢ layer(x) : Tensor⟨ (…, out) ; d ; e ; φ ; g ⟩
```

The side condition `⊨ k = in` is a *verification condition* (VC) discharged by
the SMT solver under the path's accumulated dimension constraints. If the solver
proves `k = in` **valid**, the rule fires soundly; if it finds a model of
`k ≠ in`, that model is a **counterexample** (a concrete batch/feature
assignment for which the module raises at runtime) and TensorGuard reports a
bug. If the solver returns `unknown`, the analyser abstains.

Matmul, broadcasting, `reshape` (with `−1` inference and the divisibility VC
`∏ known | numel`), normalisation, and attention rules are given analogously and
are implemented in `src/refinement/` (`attention.py`, `norms.py`, `reshape.py`,
`qkv.py`).

### 2.2 The other four theories

Device, dtype, phase and gradient are **flat lattices** `L = V ∪ {⊥, ⊤}` with
`⊥ ⊑ v ⊑ ⊤` and incomparable values. Their transfer functions are the obvious
ones: an op that requires both operands on the same device emits the VC
`d₁ = d₂`; `.to(device)`/`.cuda()` are *assignments* in the device theory;
`.float()`/`autocast` act in the dtype theory; `model.train()/eval()` set φ;
`torch.no_grad()`/`.detach()`/`requires_grad_(...)` act in g. A bug is reported
when an op's VC is refuted in any single theory; the theories are otherwise
independent, which is what makes the product *reduced* only through shared
symbolic dimensions (Section 4).

## 3. The abstract-interpretation core (numeric × type-tag × nullity)

Underneath the tensor theories, control- and value-flow within `forward` is
analysed by a classical abstract interpreter over a **reduced product** of three
domains (`src/domains/`):

* **Interval** domain `I` (`abstract_domains.Interval`, `intervals.Interval`):
  closed intervals `[lo, hi]` over `ℤ ∪ {±∞}`, with `⊥` represented by `lo > hi`
  and `⊤ = [−∞, +∞]`.
* **Type-tag** domain `T` (`typetags.py`): an antichain/hierarchy lattice over
  Python runtime types.
* **Nullity** domain `N` (`nullity.py`): `{NonNull, Null, MaybeNull}` with
  `MaybeNull = ⊤`.

### 3.1 Lattice structure (proved against the code)

Each component `D ∈ {I, T, N}` is a bounded lattice `(D, ⊑, ⊔, ⊓, ⊥, ⊤)`. The
implementation in `IntervalDomain.{leq,join,meet,bottom,top}` is verified to
satisfy, for all `a, b, c` drawn from a representative sample:

1. **Partial order.** `a ⊑ a`; `a ⊑ b ∧ b ⊑ a ⇒ a = b`; `a ⊑ b ∧ b ⊑ c ⇒ a ⊑ c`.
2. **Least upper bound.** `a ⊑ a⊔b`, `b ⊑ a⊔b`, and `a⊔b` is the least such.
3. **Greatest lower bound.** `a⊓b ⊑ a`, `a⊓b ⊑ b`, dually least-upper.
4. **Commutativity / associativity / idempotence** of `⊔` and `⊓`.
5. **Absorption.** `a ⊔ (a ⊓ b) = a` and `a ⊓ (a ⊔ b) = a`.
6. **Bounds.** `⊥ ⊑ a ⊑ ⊤`, `a ⊔ ⊥ = a`, `a ⊓ ⊤ = a`.

(`tests/test_formalization.py` checks 1–6 exhaustively on a fixed sample and via
randomised property tests.)

## 4. The reduced product and inter-theory reductions

The product domain `P = I × T × N` (`ReducedProductDomain`) lifts the lattice
operations **componentwise**:

    (i₁,t₁,n₁) ⊑ (i₂,t₂,n₂)  ⟺  i₁⊑i₂ ∧ t₁⊑t₂ ∧ n₁⊑n₂
    (i₁,t₁,n₁) ⊔ (i₂,t₂,n₂)  =   ρ( i₁⊔i₂ , t₁⊔t₂ , n₁⊔n₂ )

where `ρ` is the **reduction operator** (`ReductionEngine.reduce`) that
propagates information *between* components without leaving the represented
concretisation, e.g. `type_tag = int ⇒ nullity = NonNull`
(`TypeTagToNullityReduction`). A reduction is **sound** iff it is *reductive*
(`ρ(p) ⊑ p`) and *concretisation-preserving* (`γ(ρ(p)) = γ(p)`); the engine only
installs reductions of this form, so the product remains a valid abstraction.

Two consequences are worth stating precisely, because they are exactly what the
tests check:

* The **raw componentwise join** `(i₁⊔i₂, t₁⊔t₂, n₁⊔n₂)` is a genuine upper
  bound in the product lattice (each component join is an upper bound).
* The **reduced** join `ρ(raw)` may sit *syntactically below* the raw join,
  since reduction sharpens; it is **not** in general the syntactic least upper
  bound. What it preserves is the *concretisation*: `γ(ρ(raw)) = γ(raw) ⊇
  γ(a) ∪ γ(b)`. So the reduced product is still a **sound** abstraction of the
  union of the operands' concretisations — which is all soundness needs — even
  though `a ⊑ ρ(raw)` can fail componentwise. `meet`, by contrast, stays a lower
  bound after reduction.

## 5. Fixpoints, widening, and termination

Loop/recursive joins are computed by Kleene iteration. Because the interval
domain has infinite height, TensorGuard uses a **threshold widening** operator
`∇` (`IntervalDomain.widen`) satisfying:

* `a ⊑ a ∇ b` and `b ⊑ a ∇ b` (it is an upper bound), and
* every ascending chain `x₀ ⊑ x₁ ⊑ …` accelerated by `xᵢ₊₁ = xᵢ ∇ f(xᵢ)`
  **stabilises in finitely many steps**.

The termination property is demonstrated empirically against the real operator
in `tests/test_formalization.py` (an ever-growing chain stabilises in a bounded
number of widening steps), complementing the paper's argument that `∇` jumps to
one of finitely many thresholds (or `±∞`).

## 6. Soundness statement (informal)

> **Theorem (Soundness of `SAFE`).** If TensorGuard returns `SAFE` for a module
> `M` under an input contract `C`, then for every concrete input satisfying `C`,
> executing `M.forward` does not raise a shape/device/dtype/phase/gradient error
> in the analysed fragment.

*Proof sketch.* Each typing rule's VC is discharged as **valid** by a sound SMT
solver under the path constraints; the abstract interpreter computes an
over-approximation `γ(P) ⊇ reachable states` because every transfer function is
locally sound and `⊔`/`∇` are upper bounds; therefore no refuted VC is missed
and no reachable error state is excluded. Where any step cannot be justified
(out-of-fragment construct, `unknown` from the solver, unrecoverable source) the
analyser abstains instead of returning `SAFE`. ∎

The mechanised counterpart of the core lemmas lives under `lean/` (Step 87).
The single-shape transfer functions and the extended operator set are proved
**sound in Lean 4** and the proofs are accepted by the kernel with no `sorry`:
`lean/TensorGuard/Soundness.lean` (`applyOp_sound_linear`, `applyOp_sound_view`,
`applyOp_sound_broadcast_add`), `lean/TensorGuard/AssumeGuaranteeExtended.lean`
(`applyOpExt_sound_matmul`, `…_transpose`, `…_permute`, `…_sum_reduce`),
`lean/TensorGuard/SoundnessV5.lean` (`applyOp_sound_cross_entropy`,
`applyOp_sound_argmax`), and the operator-agnostic composition witnesses in
`MatmulSound.lean` / `BroadcastAddSound.lean`. `lean/TensorGuard/AxiomAudit.lean`
runs `#print axioms` on each of these theorems; every one depends only on the
trusted kernel axioms `{propext, Classical.choice, Quot.sound}` and never on
`sorryAx`. The precise unsound/incomplete boundary is catalogued in Step 94.
